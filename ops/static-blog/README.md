# Static blog release scripts

These scripts publish a prebuilt static site without running Node.js or reading
Notion credentials on the server.

## Inputs

GitHub Actions produces a gzip tar archive whose root contains:

- `index.html`
- `.nojekyll`
- `content-manifest.json`
- `feed.xml`
- `sitemap.xml`
- the rest of the static site

The workflow calculates the archive SHA-256 after creating it. The archive and
expected hash are transferred independently to `/opt/releases/blog/.incoming`. The deploy
script verifies the archive hash before extraction. Archives containing absolute
paths, `..` traversal, symlinks, hard links, devices, FIFOs, sockets, duplicate
entries, or excessive expanded data are rejected.

`deployment.json` is generated by the deployer and is deliberately forbidden in
the input archive. Its exact schema is:

```json
{
  "artifactSha256": "<lowercase sha256>",
  "commit": "<7-40 lowercase hex characters>",
  "repo": "owner/name",
  "runId": "<GitHub Actions numeric run id>",
  "siteUrl": "https://blog.minliny.com"
}
```

## Deploy and rollback

```bash
sudo -u minliny /opt/scripts/deploy-static-blog.sh \
  /opt/releases/blog/.incoming/blog-abc1234-123.tar.gz \
  <sha256> \
  minliny/minliny.github.io \
  abc1234 \
  123 \
  https://blog.minliny.com

sudo -u minliny /opt/scripts/rollback-static-blog.sh abc1234-123
```

The deployer copies `source/.` so dotfiles are preserved, verifies the staged
release offline, renames it to the immutable `commit-runId` directory, and then
atomically replaces `/srv/blog/current` through a temporary symlink. It fetches
five files through the local web server and compares their hashes with the new
release. A failed HTTP check restores the previous symlink. Rollback follows the
same checks and verifies its target before changing the symlink. No script
deletes a completed release.

Replaying the same `commit + runId` is safe when repository, site URL, artifact
SHA-256, and the complete `deployment.json` identity match. The existing release
is verified again and activated if necessary. Any identity or hash mismatch is
rejected without modifying `current`.

The activation probe uses a dedicated loopback-only HTTP virtual host. This
keeps origin-certificate and hairpin-routing differences out of the atomic
release gate without weakening public HTTPS. Install this server block through
the normal administrator-managed Nginx configuration:

```nginx
server {
    listen 127.0.0.1:8080;
    server_name blog.minliny.com;
    root /srv/blog/current;

    access_log off;

    location ~ ^/(deployment\.json|index\.html|content-manifest\.json|feed\.xml|sitemap\.xml)$ {
        try_files $uri =404;
    }

    location / {
        return 404;
    }
}
```

The default probe is `http://127.0.0.1:8080` with `Host: blog.minliny.com`.
It downloads only `deployment.json`, `index.html`, `content-manifest.json`,
`feed.xml`, and `sitemap.xml`, then compares every response with the selected
release by SHA-256. There is no insecure TLS mode. Public certificate, routing,
and CDN behavior remain the responsibility of the external post-deploy smoke
check, which must continue to use ordinary certificate validation.

Adding the Nginx listener and reloading Nginx is a one-time administrator task.
The deploy user only connects to an unprivileged loopback port and needs no
`sudo` access. Do not grant the forced-command key passwordless `sudo` or write
access to Nginx configuration.

After installing the server block, validate it as follows:

```bash
nginx -t
systemctl reload nginx
ss -ltn | grep '127.0.0.1:8080'

test_dir="$(mktemp -d)"
for file in deployment.json index.html content-manifest.json feed.xml sitemap.xml; do
  curl --fail --silent --show-error \
    --header 'Host: blog.minliny.com' \
    --output "$test_dir/$file" \
    "http://127.0.0.1:8080/$file"
  cmp --silent "$test_dir/$file" "/srv/blog/current/$file"
done
rm -rf -- "$test_dir"
```

The socket listing must show only `127.0.0.1:8080`, never `0.0.0.0:8080` or
`[::]:8080`. A connection to the server's public IP on port 8080 must fail.
Run the public HTTPS smoke from outside the origin so it exercises the real
certificate path rather than the server's hairpin route.

Deploy and rollback hold an exclusive `flock` for their full execution. A
deployment arms an EXIT/HUP/INT/TERM recovery trap before changing `current` and
disarms it only after HTTP verification succeeds, so an SSH interruption after
the switch restores the previous symlink. Completed releases are retained even
when activation fails.

## GitHub Actions forced command

`github-blog-deploy-entrypoint.sh` is intended as the only command permitted by
the Actions deployment public key. It accepts the tar archive on standard input
and accepts only this exact original-command grammar:

```text
deploy <40-lowercase-hex-commit> <numeric-run-id> <64-lowercase-hex-sha256>
```

An `authorized_keys` line should use the absolute installed script path and
disable all SSH side channels:

```text
restrict,command="/opt/scripts/github-blog-deploy-entrypoint.sh" ssh-ed25519 AAAA... github-blog-deploy
```

On OpenSSH versions without `restrict`, use
`no-agent-forwarding,no-port-forwarding,no-X11-forwarding,no-pty,no-user-rc`
with the same forced `command=`. The entrypoint fixes the repository, primary
site URL, release paths, loopback health endpoint, resource limits, and lock
policy before loading shared code. It rejects every other command, ignores SSH
environment overrides for those values, limits stdin size, verifies its SHA-256,
and atomically creates the incoming archive before invoking the deployer. This
key never receives a general shell.

## Self-test

The self-test uses only a temporary directory and a loopback Python HTTP server:

```bash
./test-static-blog-release.sh
```
